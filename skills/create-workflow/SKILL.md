# Axhub Make 创建内容工作流

你正在协助用户在 Axhub Make 中创建或更新项目资源。这个 Skill 是入口分流器：先判断用户真正要产出的主资源，再按需加载一个最相关的引用文档。不要把它当成最终实现规范；具体实现细节由引用文档接管。

## 进入条件

当用户提出以下任一目标时使用本 Skill：

- 创建或更新原型、页面、业务组件、通用 UI 组件。
- 创建 PRD、需求说明、使用手册、设计说明、项目文档。
- 创建 需求调研、调研报告、调研文档、需求分析、需求收集、用户需求分析。
- 创建主题、设计系统、配色、design token、全局 CSS 变量。
- 创建 JSON 数据表、mock 数据、示例数据或页面可消费数据。
- 用户只说“帮我做一个 / 新建一个 / 生成一个”，且上下文指向 Axhub Make 项目资源。

## 核心原则

- **先读项目规则**：开始前必须阅读 `/AGENTS.md`，确认目录、同步文档、验收等项目级约束。
- **主产物优先**：一次请求先确定一个主产物；其他资料默认作为上下文，不自动切换工作流。
- **渐进加载**：默认只加载一个引用文档。只有用户明确要求多个独立产物，或当前产物必须依赖另一类资源，才补充加载第二个引用文档。
- **能做就做**：如果用户已给出足够需求，不要停在建议或计划；继续执行对应引用文档的创建流程。
- **缺口才澄清**：只有目标类型、输出位置或关键业务内容不明确且无法从项目上下文推断时，才向用户提一个简短问题。
- **文档代码同步**：涉及原型/组件时，`spec.md` 与实现代码必须同步更新；涉及资源规范时，按对应目录规则落地。

## 执行流程

1. **读取上下文**
   - 输入：用户当前请求。
   - 动作：阅读 `/AGENTS.md`；必要时查看当前目录中已有同类资源。
   - 输出：确认项目级约束和候选产物类型。

2. **识别主产物**
   - 输入：用户关键词、目标目录、文件类型、上下文资料。
   - 动作：按“意图分流”和“分流优先级”确定主产物。
   - 输出：一个主工作流类型：`prototype`、`document`、`requirement-research`、`theme` 或 `data`。

3. **加载引用文档**
   - 输入：主工作流类型。
   - 动作：只读取对应的 `./references/create-*.md`。
   - 输出：后续创建流程所需的具体规范。

4. **判断是否需要澄清**
   - 如果用户缺少最小必要信息，使用“模糊意图回复模板”或引用文档中的对齐模板。
   - 如果信息已足够，直接继续引用文档的流程，不重复追问。

5. **执行创建与验收**
   - 按引用文档要求创建或更新文件。
   - 执行可用的验收流程，例如读取规范、检查文件结构、运行类型检查/构建/页面验收。
   - 最终回复说明产物路径、验收结果和仍需用户确认的业务点。

## 意图分流

| 用户意图 / 关键词 | 加载文档 | 典型产物 |
| --- | --- | --- |
| 原型、页面、组件、做个页面、做个组件 | `./references/create-prototype.md` | `src/prototypes/...` 或 `src/components/...` |
| 文档、PRD、说明文档、需求文档、手册 | `./references/create-document.md` | `src/resources/...` |
| 主题、设计系统、配色、design token、DESIGN.md | `./references/create-theme.md` | `src/themes/...` |
| 数据、数据表、JSON、mock 数据、示例数据 | `./references/create-data.md` | `src/database/...` |
| 需求调研、调研报告、调研文档、需求分析、需求收集、用户需求分析 | `./references/create-requirement-research-document.md` | `src/resources/...` |

## 分流优先级

1. 用户明确点名输出目录或文件类型时，按目标产物分流：
   - 提到 `spec.md`、`index.tsx`、页面、组件 -> 原型 / 组件
   - 提到 `DESIGN.md`、`designToken.json`、`globals.css` -> 主题
   - 提到 `.json` 数据表、`records`、mock 数据 -> 数据
   - 提到 PRD、说明文档、手册、Markdown、报告、调研 -> 文档
2. 如果同一提示里既有“创建原型”又有“参考主题 / 文档 / 数据”，优先加载原型工作流，把主题 / 文档 / 数据当作上下文资料。
3. 如果同一提示里既有“调研报告”又有“参考主题 / 文档 / 数据”，优先加载原型工作流，把主题 / 文档 / 数据当作上下文资料。
4. 如果同一提示明确要求多个独立产物，例如“创建页面并新增一张可复用数据表”，先处理主产物，再加载第二个引用文档处理附属产物。
5. 如果用户只说“帮我创建一个”，目标不明确时，不要盲猜，先用下方模板补齐。

## 多产物处理规则

- **页面 + 数据**：主产物通常是原型；数据若需要长期复用或用户明确要求数据表，再补充读取 `create-data.md`。
- **页面 + 主题**：主产物通常是原型；主题作为参考，除非用户明确要求新增主题文件。
- **文档 + 配图**：主产物是文档；配图作为 `src/resources/assets/` 附属资源处理。
- **组件 + 使用文档**：主产物是组件；组件说明优先写入组件 `spec.md`，除非用户明确要求单独项目文档。

## 异常与边界处理

- 如果 `/AGENTS.md` 不存在，改读仓库根目录下可用的 `CLAUDE.md` 或 `README.md`，并在最终回复说明 fallback。
- 如果引用文档不存在，停止创建，告知缺失路径，并不要臆造该流程。
- 如果用户指定的目录与分流结果冲突，以明确目录为准，并在回复中说明判断依据。
- 如果需求涉及修改已有资源，先读取现有文件，再按“更新”处理；不要覆盖用户已有内容。
- 如果用户要求跳过验收，仍至少做静态检查，并说明未执行完整验收的原因。

## 模糊意图时的首次回复模板

```text
收到，我可以帮你创建内容。

先告诉我这次主要要创建哪一类：
1. 原型 / 组件
2. 文档 / 调研
3. 主题
4. 数据表

再补一句你的目标和使用场景，我就按对应流程继续。
```

## 最终回复要求

完成创建或更新后，回复应包含：

- 主产物类型和已加载的引用文档。
- 新增或修改的关键文件路径。
- 已完成的验收动作与结果。
- 需要用户确认的业务假设或遗留问题。
