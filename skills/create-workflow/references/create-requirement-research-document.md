# 创建需求调研文档

创建或更新需求调研类文档的标准流程。文档默认存放在 `src/resources/`，调研截图、流程图、访谈材料等附属资源默认存放在 `src/resources/assets/`。

## 角色定位

你将作为 **需求分析师 × 产品经理（复合型）**，把业务访谈、会议纪要、原型说明、系统现状、运营反馈、数据口径和流程痛点整理成可评审、可追溯、可继续转化为 PRD 的需求调研文档。

核心职责：

- 还原业务现状与真实问题。
- 识别干系人、角色、场景、流程与系统边界。
- 提炼痛点、根因、诉求与需求机会。
- 标注信息缺口、冲突点和待确认事项。
- 为 PRD、原型设计、研发评审和排期决策提供可信输入。

## 适用范围

当主产物被 `create-workflow` 判断为 `requirement-research` 时使用本流程，包括：

- 需求调研报告、调研文档、需求分析。
- 用户访谈纪要、会议纪要结构化整理。
- 业务现状与痛点分析、系统现状调研。
- 业务流程、角色权限、数据指标、问题清单与需求机会分析。
- 对 `src/resources/` 下已有调研文档进行补充、修订、拆分或结构化整理。

如果用户实际要创建 PRD、页面说明、技术方案、接口文档、测试用例、原型页面或数据库结构，应回到 `create-workflow` 重新分流。

## 核心原则

- **先读规范**：必须阅读 `AGENTS.md`、`rules/resource-management-guide.md`、`rules/documentation-guide.md`。
- **先调研后方案**：调研文档以“现状、问题、证据、诉求、机会、待确认”为主，不替代 PRD。
- **不编造结论**：材料没有支撑的内容标记为 `待确认`，不得臆造业务规则、系统能力或组织决策。
- **问题可追溯**：每个需求机会应能回溯到现状、痛点、访谈反馈、会议结论、原型、数据或业务材料。
- **单篇优先**：默认只创建或更新当前主题的调研文档，不主动扩展成完整项目文档体系。
- **结构服务评审**：文档要便于产品、研发、测试、运营、业务方共同评审。
- **保留冲突**：不同材料存在冲突时，不自行裁决，应列入“冲突点与待确认事项”。
- **可转 PRD**：调研结论应沉淀为后续 PRD 可复用的业务范围、角色场景、流程、规则、字段、异常和验收关注点。

## 执行流程

1. **读取规则与资料**
   - 输入：用户需求、附件、会议纪要、访谈记录、原型、截图、链接、历史文档、业务背景。
   - 动作：阅读项目规则和文档规范；查找相关已有文档、原型、数据表、PRD、流程说明。
   - 输出：资料清单、调研主题、调研边界、候选输出路径。

2. **判断新建还是更新**
   - 用户指定已有文件时，读取原文并按更新处理。
   - `src/resources/` 已有高度相似文档时，提示可更新现有文档；除非用户明确要求新建。
   - 存在同名文件时，先读取原文，再询问更新、改名新建还是合并。

3. **需求对齐**
   - 信息足够时直接继续，不重复追问。
   - 缺少调研主题、目标、读者、业务范围、材料来源或输出粒度时，使用“最小澄清模板”一次性补齐。

4. **识别调研对象与业务边界**
   - 明确业务域、系统或端口、组织部门、用户角色、主流程、异常流程、数据对象、状态、权限和规则。
   - 明确包含范围和不包含范围；边界不清时标记 `待确认`。

5. **提取现状、痛点与证据**
   - 从材料中拆分业务现状、系统现状、线下操作、协作方式、数据流转、审批流转、痛点、影响、根因和证据。
   - 避免只写“效率低”“体验差”，必须写清发生场景、影响对象和具体表现。

6. **提炼需求机会**
   - 将痛点转化为初步需求机会，但不写成最终 PRD。
   - 每条需求机会包含：诉求、目标角色、触发场景、改进方向、涉及系统、初步优先级、依赖、风险与待确认。

7. **选择模板**
   - 按“模板选择规则”选择最小够用模板。
   - 只读取当前需要的模板，不一次性加载所有模板。
   - 模板缺失时，使用 `src/resources/templates/standard-research-documents-template.md` 中的通用结构。

8. **生成或更新文档**
   - 新建：在 `src/resources/<doc-name>.md` 写入完整 Markdown。
   - 更新：在原文基础上补充、修订或重排，保留仍有效的历史结论。
   - 图片和附件放入 `src/resources/assets/`，Markdown 引用写 `assets/<文件名>`。

9. **验收**
   - 检查标题层级、模板占位符、图片路径、链接路径、资料来源、待确认标注、冲突点、风险确认对象。
   - 最终回复说明文档路径、资料来源、处理方式、完成内容、质量检查和待确认事项。

## 最小澄清模板

仅在关键信息不足时使用：

```text
收到，准备创建需求调研文档。

我还需要确认 4 点：
- 调研主题：聚焦哪个业务、系统或流程？
- 调研目标：用于立项、PRD 前置分析、流程重构、评审汇报，还是问题沉淀？
- 目标读者：产品 / 研发 / 测试 / 运营 / 业务方 / 管理层 / 财务 / 法务
- 已有材料：是否有会议纪要、访谈记录、原型、截图、数据表或历史文档？
```

如果用户已提供足够材料，不要使用该模板拦住流程。

## 模板选择规则

| 文档用途 | 建议模板 |
| --- | --- |
| 需求调研报告 | `src/resources/templates/requirement-research-template.md` |
| 业务访谈纪要 | `src/resources/templates/interview-notes-template.md` |
| 业务流程调研 | `src/resources/templates/business-flow-research-template.md` |
| 系统现状调研 | `src/resources/templates/system-current-state-template.md` |
| 数据指标调研 | `src/resources/templates/data-research-template.md` |
| 用户角色调研 | `src/resources/templates/user-role-research-template.md` |
| 问题清单与需求机会 | `src/resources/templates/problem-opportunity-template.md` |
| 不确定用哪类 | `src/resources/templates/standard-research-documents-template.md` |

使用模板时遵守：

- 先读取模板，再按当前业务裁剪。
- 不保留 `{{placeholder}}`、空章节或与当前调研无关的模板段落。
- 更新已有文档时，优先沿用原文件结构；只有结构明显不适合时才引入模板。

## 调研信息提炼规则

### 从会议纪要提炼

拆分为背景、目标、现状问题、角色诉求、已确认结论、待办事项、争议点和后续行动。不要直接全文粘贴会议纪要。

### 从原型或截图提炼

拆分为页面入口、使用角色、页面目标、信息展示、操作路径、字段规则、状态变化、异常反馈、跨系统关系。不确定的控件逻辑标记 `待确认`。

### 从用户口述提炼

将口述转化为“明确事实、推断结论、待确认问题”：

| 原始表述 | 处理方式 |
| --- | --- |
| 现在都是线下处理，很麻烦 | 现状：流程依赖线下处理；痛点：缺少线上流程与留痕；待确认：具体节点、角色、耗时 |
| 财务那边经常对不上 | 问题：账实核对存在差异；待确认：差异类型、发生频率、涉及系统、金额影响 |
| 后面要做成自动化 | 需求机会：流程自动化；待确认：自动化边界、触发条件、审批规则、异常兜底 |

### 从已有 PRD 提炼

区分已上线能力、已设计未上线能力、评审中能力、未来规划能力、可复用规则和与当前业务冲突的旧规则。

## 文件命名与位置

- 默认目录：`src/resources/`。
- 推荐文件名：
  - `<业务主题>-需求调研文档.md`
  - `<业务主题>-调研报告.md`
  - `<业务主题>-现状与痛点分析.md`
  - `<业务主题>-问题清单与需求机会.md`
- 文件名应与项目既有风格一致，可使用中文业务名。
- 不把调研文档放到 `src/prototypes/`、`src/components/` 或 `src/database/`。

## 新建文档要求

新建需求调研文档至少包含：

- 一级标题、文档信息、背景与目标、范围与非目标。
- 干系人、业务角色、当前业务现状、当前系统现状。
- 主流程、异常流程、跨部门协作。
- 核心痛点、影响、根因和证据来源。
- 需求诉求与需求机会。
- 字段、状态、权限、流程、数据口径等规则发现。
- 风险与约束、冲突点、待确认事项、后续建议。

## 更新文档要求

- 先读取原文，识别现有结构、术语、引用和结论。
- 保留仍有效的历史调研结论。
- 对过期内容使用“已过期”“需复核”“已被新结论替代”等方式标记或替换。
- 新增内容优先追加到对应章节，不破坏原文结构。
- 若用户只要求补充某个模块，不主动重写整篇文档。
- 若需要大幅重构，先说明重构范围和原因。

## 图片与附属资源规则

- 图片和附件统一放在 `src/resources/assets/`。
- Markdown 引用使用 `assets/<文件名>`，例如 `![当前业务流程](assets/shop-current-flow.png)`。
- 不使用临时路径、绝对本机路径、base64 图片或外部临时链接。

## 异常与边界处理

- `rules/documentation-guide.md` 缺失：继续读取 `rules/resource-management-guide.md` 和现有同类文档，最终回复说明 fallback。
- 调研模板缺失：使用 `standard-research-documents-template.md` 的通用结构，并在最终回复说明未使用专用模板。
- 用户资料冲突：列出冲突点，标为 `待确认`，不要自行裁决关键业务规则。
- 已有同名文件：先读取并询问是更新、改名新建还是合并。
- 需求过大：先产出文档目录和拆分建议，再按用户确认范围落地。
- 资料过少：先生成调研提纲、访谈问题清单或待补充资料清单。
- 涉及法律、财务、合规等高风险内容：只整理用户资料，不编造政策结论，并标注需业务 / 法务 / 财务确认。

## 最终回复要求

完成后，最终回复应包含：

- 文档路径。
- 新建还是更新。
- 使用的资料来源。
- 已完成的主要内容。
- 已完成的质量检查。
- 仍需用户确认的问题。

- [ ] 已阅读 `AGENTS.md`、`rules/resource-management-guide.md`、`rules/documentation-guide.md`。
- [ ] 已确认新建或更新，并检查同名 / 同主题文档。
- [ ] 已按需读取会议纪要、访谈记录、原型、数据、PRD 或已有文档。
- [ ] 已明确调研主题、目标、范围和目标读者。
- [ ] 已识别干系人、业务角色和系统边界。
- [ ] 已区分业务现状、系统现状、痛点、根因、需求机会。
- [ ] 已将无依据内容标记为 `待确认`。
- [ ] 已列出资料冲突点，未自行裁决关键业务规则。
- [ ] 已沉淀字段、状态、权限、流程或数据口径等可转 PRD 信息。
- [ ] 已选择合适模板或明确使用通用结构。
- [ ] 文档中没有未替换模板占位符。
- [ ] 图片和链接使用稳定相对路径。
- [ ] 涉及法律、财务、合规等高风险内容已标注需确认。
- [ ] 最终回复包含文档路径、验收结果和待确认事项。
